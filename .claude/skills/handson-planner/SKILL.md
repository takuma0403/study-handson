# ハンズオン学習計画

広いテーマや「次は何をやる？」に対して、リポジトリの過去セッションとユーザーの今の理解を踏まえ、応用ゴールから基礎まで逆算したロードマップを作る。各項目は handson スキルの1セッションとして始められるサイズにする。

## 最初に読むもの（ユーザーに聞く前に）
- `sessions/*/plan.md` の frontmatter（theme, concepts, prerequisites, status, date, roadmap_id）
- `sessions/*/summary.md` の「まだ分からないこと」とレビュー状態
- `sessions/*/log.md` で判定が ⚠️ / ❌ だった箇所と「後回し」
- `roadmaps/*.md`

読んだ結果を、概念ごとに次の3つに分ける。
- 理解済み：総括で合格し、誤りの指摘が残っていない
- 曖昧：⚠️ / ❌ のまま、または「まだ分からないこと」に挙がっている
- 未着手：記録にない

## フロー

### 1. 状況を伝える
今どこまで進んでいるかを短く伝える（例：「Dockerは3回やりました。ネットワークは理解済み、ボリュームはまだ曖昧です」）。記録が何もなければ、初回だと伝える。

### 2. ゴールを決める（広いテーマのとき）
- 「勉強したい」だけではゴールにならない。手を動かしてできる応用ゴールを、具体例3つから選んでもらう。
  - 例（Go）：CLIツールを作れる / REST APIを書いてテストできる / goroutineとchannelで並行処理を設計できる
- 使える時間の感覚（週に何回、1回何分）も聞く。
- 聞くことは一度にまとめる。

### 3. 現状を診断する
- 記録で分からない前提だけを、2〜4問の「説明してみて」で確かめる（例：「イメージとコンテナの違いを一言で」）。
- 正誤の採点ではなく、状態の判定に使う：説明できる → 理解済み、半分 → 曖昧、知らない → 未着手。
- 記録で理解済みのものは聞き直さない。古い記録（目安3か月以上前）は1問だけ確認してよい。

### 4. 逆算する
- ゴール → 必要なスキル → その前提…と、ユーザーの現在地まで分解する。
- 各項目を1セッション（60〜90分、ローカル完結）にまとめる。大きすぎれば分け、小さすぎれば合わせる。
- 理解済みは計画に入れない（skip）。曖昧なものは短い復習セッションにする。
- 関連テーマは「必須」と「知っていると深まる」を分けて示す（例：Docker → Linuxのnamespace/cgroup、ネットワークの基礎）。別テーマのロードマップがあればつなぐ。
- 最初の計画は5〜10セッションにとどめる。先は進んでから計画し直す。

### 5. 提案する
- 依存関係の図（mermaid）とセッションの表を示す。
- 「次のおすすめ」を1つ、代わりの候補を2つ出す。理由には記録の根拠を添える（例：「11/10の総括で『ボリュームとバインドマウントの違いが曖昧』とあったので」）。
- 計画は提案であり、決めるのはユーザー。並びや粒度の調整に応じる。

### 6. 保存して渡す
- 合意した内容を `roadmaps/<theme>.md` に保存する（あれば更新する）。
- 次のセッションの開始コマンドを渡す：`/handson <ロードマップID> <セッションのタイトル>`

## roadmap の形式
```
---
theme: docker
goal: 自作のWebアプリをcomposeで開発環境として動かし、不具合の原因を切り分けられる
updated: 2026-11-17
---
## 依存図
（mermaid）
## セッション
| ID | タイトル | ゴール（終わったら説明できること） | 前提 | 状態 | 記録 |
|---|---|---|---|---|---|
| D1 | イメージとコンテナ | ... | - | done | sessions/2026-11-03-... |
| D2 | ボリューム | ... | D1 | review | sessions/2026-11-10-... |
| D3 | composeで複数コンテナ | ... | D1,D2 | todo | |
## 関連テーマ
- 必須：...
- 知っていると深まる：...
## 後回し・疑問
- [ ] ...
```
状態は done / review（曖昧） / todo / skip（理解済み） の4つ。

## テーマを指定せずに「次は何をやる？」と聞かれたとき
すべてのロードマップを見渡し、次の順で選ぶ。
1. in-progress / paused のセッション（続きから）
2. review の項目（曖昧なままにしない）
3. 前提がそろった todo のうち、ゴールに一番効くもの
4. 「後回し・疑問」から広げる価値のあるもの

## 注意
- 技術のバージョンや推奨の方法は変わる。新しさが重要な内容は「要確認」と書き、ハンズオンの中で確かめさせる。
- 記録にない理解を推測で「理解済み」にしない。
